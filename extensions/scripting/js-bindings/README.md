# Axmol native JavaScript

This extension adds native JavaScript to Axmol with the Cocos SpiderMonkey
33.1 API (upstream version string `33.1.1`). It uses generated JSAPI bindings
against current Axmol headers, with explicit adapters for Cocos2d-x v3 behavior.
`cc`, `ccui`, `ccs`, `sp` and `jsb` remain the script namespaces.

JavaScript is opt-in: `AX_ENABLE_EXT_JS` defaults to `OFF`. Applications link
`axjs` explicitly; turning the option off does not import SpiderMonkey. Lua and
JS can be compiled into the same SDK, while an application registers one active
`ScriptEngineProtocol` implementation.

## Build and create a project

Build a runtime package for each target architecture first. See
[the runtime build instructions](../../../tools/js-runtime/README.md) for the
pinned source, verified archive, patches, Python 2 bootstrap, Android NDK and
Apple deployment settings. Axmol and its JS bindings remain C++23; only the
isolated SpiderMonkey library uses C++11.

From the engine checkout:

```sh
python3 tools/js-runtime/bootstrap-python2.py
python3 tools/js-runtime/build.py --platform macos --arch arm64
pwsh tools/cmdline/axmol.ps1 new HelloJs -l js -d /path/to/projects
```

The template enables JS and registers the bindings, loads
`script/jsb_boot.js`, then runs `main.js`. `project.json` controls `jsList`, FPS
and the frame interval. Native platform projects come from the common Axmol
template. See [the JS template](../../../templates/js/README.md) for source
builds, prebuilt SDKs and target-specific settings. Set
`AX_JS_SPIDERMONKEY_ROOT` to the matching package when configuring CMake.

A minimal custom native entry point is:

```cpp
#include "js-bindings/runtime/JsEngine.h"
#include "js-bindings/manual/Bindings.h"

auto* engine = ax::JsEngine::getInstance();
ax::ScriptEngineManager::getInstance()->setScriptEngine(engine);
engine->addRegisterCallback(axjs::registerAll);
if (!engine->start() || !engine->runScript("script/jsb_boot.js") ||
    !engine->runScript("main.js")) {
    // Report startup failure to the application's host.
}
```

Create the render view before scripts that render scenes. Package the entire
`script` directory with the application, including the legacy adapters and
CocoStudio parsers. The template's CMake helpers perform that resource copy.

## Runtime and binding contracts

- Each live native `ax::Object` has one JS wrapper per VM. Wrappers use native
  weak-handle generations and reject access after destruction or address reuse.
- Factory results retain their normal native autorelease behavior. Constructors
  autorelease once; getters do not retain. Explicit `retain()` / `release()`
  remain available. Native-object GC ownership is not enabled in this version.
- `.extend()`, `ctor` and `_super()` use current native prototypes. Node entry,
  exit, cleanup and update dispatch before native execution; `_super()` invokes
  the real base implementation with a per-node, per-method reentry guard.
- JS node updates use Axmol's Scheduler and its priorities, pause/resume and
  cleanup rules. Timers and callback functions keep their JS receiver alive.
  Stopping a VM invalidates callbacks before dropping roots and removes the
  manually registered JS timers and listeners.
- JS executes on the VM owner thread. Worker-thread callback destruction queues
  root release to that thread. `JS_Init` / `JS_ShutDown` are process-wide;
  restarting a VM recreates its context and runtime.
- Input/custom/hot-update events borrowed for a callback expire at its end.
  Spine bone, slot and track handles carry owner/track lifetime tokens; disposed
  tracks and replaced skeleton assets invalidate old handles.
- `.jsc` is tried before `.js`. Invalid bytecode falls back to source when it
  exists, otherwise loading fails. Use the package's `axmol-jscompile` for new
  bytecode. The [historical bytecode fixture](../../../tools/js-tests/runtime-audits/legacy-bytecode/README.md)
  was generated by the pinned old Cocos macOS x64 dependency and decoded by
  the rebuilt ARM64 runtime. Its compiler recipe, sample and source checksums
  are included. Other old projects still need a sample compatibility test;
  the shared version name alone does not establish compatibility.

## Migrate a Cocos2d-x v3 project

Start from a new JS native project and copy business scripts and resources into
its `Content` directory. Preserve their logical filenames and `project.json`
entries. Port custom native extensions through the generator or a manual
registration callback. Rebuild third-party native SDK integrations with the
new platform project.

| Area | Migration behavior |
| --- | --- |
| Core 2D / UI | Current native classes plus legacy constructors, properties, factories, menu/UI callbacks and event descriptors. |
| Input | Old touch/mouse descriptors adapt to Axmol pointer events; keyboard and custom events retain JS callback conventions. |
| Audio | `cc.audioEngine` wraps current `cc.AudioEngine`; new code may use the generated engine directly. |
| CocoStudio | `ccs.load()` returns `{node, action}`. JSON uses the retained licensed Cocos parsers; CSB uses current CSLoader. Controller callback names/types are bound to native widgets. |
| Spine | Re-export assets with Spine **4.3**. The old 3.6 runtime is not bundled. Native resource changes are not solved by JS API aliases. |
| Hot update | `jsb.AssetsManager`, manifests, events, verification callbacks and search paths use Axmol's assets manager. `jsb.restart()` recreates the VM and runs bootstrap/main again on the engine thread. |
| Reflection | `jsb.reflection.callStaticMethod` uses JNI signatures on Android and Objective-C selectors on Apple. See the template's bridge examples and Android keep rules. |
| Debugger | Use the [VS Code DAP extension](../../../tools/js-debugger/README.md); debugger services compile only in development configurations. |

This compatibility layer targets native JS business source. Native build files,
third-party SDKs, resource formats and custom rendering can require changes.
It does not include browser support, 32-bit Android, a new ARM64 JIT, old
Chipmunk/Socket.IO, 3D/NavMesh bindings or old direct OpenGL/shader interfaces.
JavaScript syntax and built-ins are those supported by SpiderMonkey 33.1.

## Platforms and execution modes

| Target | Architectures | JS execution |
| --- | --- | --- |
| Android, NDK r27d / API 23 / shared libc++ | arm64-v8a, x86_64 | ARM64 interpreter; x86_64 Baseline/Ion |
| macOS | arm64, x86_64 | ARM64 interpreter; x86_64 Baseline/Ion |
| iOS device / simulator | device arm64; simulator arm64, x86_64 | Interpreter on all architectures |

Packages are architecture-specific and carry matching generated headers and a
validated manifest. ARM64 performance must be measured separately from x64 JIT.
The macOS x64 JIT requires the supplied allow-jit entitlement for hardened
applications. Build success, an isolated runtime smoke and a full application
run are distinct checks; consult the runtime documentation and test results
for which targets have actually executed.

## Generate and validate

[JS generator documentation](../../../tools/js-bindings/README.md) describes
`axmol genbindings -l js`, module configuration, generated API manifests and
manual adapter policy. Omitting the language retains Lua generation. Generated
files are committed output; make fixes in the emitter/configuration and
regenerate instead of editing a generated shard.

[Runtime regressions](../../../tests/js-runtime-tests) exercise real
SpiderMonkey and native ownership. [JS application tests](../../../tests/js-tests/README.md)
cover generated bindings, lifecycle compatibility, scenes and an unchanged
Cocos v3 HelloWorld fixture. The debugger has DAP and actor tests in `tools/js-debugger/test`. Tests must report exceptions and
nonzero exits; a successful C++ compile is not sufficient compatibility proof.
